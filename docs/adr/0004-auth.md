# ADR 0004: Better Auth for identity, our RLS tables for tenancy

- Status: accepted (P3, 2026-11-21)
- Deciders: owner, with Claude Code

## Context

Section 2 names Better Auth and suggests mapping its organization plugin onto our tenants. Section 3 requires every tenant table to sit behind forced RLS and `withTenant`, with one global identity per person and sessions scoped to the tenant host.

Better Auth talks to the database through its own adapter, which has no per-query hook. It therefore cannot run inside `withTenant` (`SET LOCAL ROLE app_user` plus `app.tenant_id`). Its organization plugin reads and writes members and invitations for every organization, which would need a role that sees all tenants' memberships outside RLS. Its docs also don't confirm renaming those tables.

## Decision

- **Better Auth owns identity only:** users, credential accounts, sessions, verifications, TOTP secrets, passkeys and rate-limit counters.
  - It reaches them through a dedicated role, `app_auth` (NOLOGIN, NOBYPASSRLS), and a separate pool that connects as `app_login` with `-c role=app_auth`.
  - `app_auth` has grants on those tables only, plus a few columns of `tenants`.
  - Every identity table has forced RLS: `app_auth` sees all rows, and other roles see none, except `app_user`'s view of `users` (next point).
- **Tenancy stays in our tables:** `memberships`, `invitations` and the append-only `audit_logs` are ordinary tenant tables, written only inside `withTenant`. `app_user` may read a few columns of `users`, and only for members of the current tenant. The organization plugin is not used.
- **The admission hook** is Better Auth's `session.create.before`, in `src/modules/auth/admission.ts`. It:
  - binds every new session to the tenant of the request host (the proxy's trusted `x-tenant-id`, or the platform tenant on the Hub);
  - applies the tenant's registration mode, invitations, membership status and admin method rules (`policy.ts`, unit-tested);
  - writes memberships and the audit entry in the same tenant transaction.
- **`getTenantSession(tenantId)`** rejects a session bound to another tenant, past the tenant's session length, or an impersonation past its deadline.
- **Sign-in methods:**
  - Password: Argon2id, plus a breached-password check in staging and production.
  - Magic link, TOTP 2FA and passkeys.
  - Google and Microsoft OAuth, when their credentials are set.
- **Admin two-step verification:** admin roles (tenant admin, program manager, platform staff) must use password + TOTP or a passkey. Magic links are refused for them, and so is OAuth outside SSO-only tenants. Admin pages send admins without a second factor to account security.
- **Versions:** Better Auth is pinned to 1.7.18. The newest release was inside pnpm's minimum-release-age window, so it waits.

## Consequences

- No role can read every tenant's memberships. Better Auth's identity data and our tenant data are separated by database role, not only by code.
- One person has one set of credentials across partners, but each session works on one host only. Cookies are host-only, and the server checks the binding.
- **Passkeys** use the root domain as the relying party, so they work on the Hub and on subdomain tenants.
  - Custom domains would need their own relying party. Not supported yet.
  - Browsers refuse `localhost` as a relying party for `*.localhost`, so local passkey testing needs a registrable root domain such as `lvh.me`.
  - Accepted origins are added at runtime from proxy-validated hosts (`passkey-origins.ts`).
- **Connections:** the auth pool needs a direct or session-mode connection, because transaction-mode poolers drop startup options. Inside Better Auth hooks, code must not wait for a second `app_auth` connection: it reads users through Better Auth's adapter instead, which avoids a pool deadlock under load.
- **Revisit** if Better Auth adds per-request adapter hooks, or if the organization plugin supports custom table and field mapping with tenant scoping.
